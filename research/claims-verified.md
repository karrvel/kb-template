## Karpathy LLM-wiki pattern (30)

- **[2026-04-16|blog]** The article frames the LLM wiki via a compiler analogy: RAG is 'interpreted execution' (stateless per-query re-derivation) while the wiki is 'compiled execution' where raw sources are pre-compiled into optimized wiki-page artifacts ahead of time.

- **[2026-04-16|blog]** The wiki beats RAG for compounding knowledge because new sources update existing concept pages and add cross-references at ingestion time, whereas RAG re-derives everything statelessly on each query with no memory of prior queries.
- **[2026-04-03|secondary]** Karpathy's LLM wiki pattern treats the LLM as a compiler that ingests raw source documents from a raw/ staging directory and emits a structured, interlinked markdown wiki (concept articles with backlinks and cross-references), directly instantiating the compiler analogy where raw sources are source code and the wiki is the compiled artifact.
- **[2026-04-03|secondary]** At personal-knowledge-base scale (~100 articles), no vector database is required; index files plus the LLM context window are sufficient for retrieval, which is the article's explicit argument for why the plain-markdown wiki approach can supplant a RAG/vector pipeline.
- **[2026-04-03|secondary]** The system produces compounding knowledge because every query, chart, and answer is filed back into the wiki, so explorations accumulate rather than being discarded after a session.
- **[2026-04-03|secondary]** The wiki-compiler workflow is a cyclical loop of distinct phases: Ingest (raw sources into a raw/ directory), Compile (LLM produces index files, concept articles, and maintains a link graph), Query & Enhance (browse/ask and file answers back), and Lint & Maintain (health checks, impute missing data, suggest new articles).
- **[2026-04-12|blog]** Karpathy's LLM Wiki pattern rests on a compiler analogy: raw sources are treated as source code that must be 'compiled' into a wiki artifact, in contrast to RAG which runs directly against raw source.

## MemGPT / Letta tiered memory (27)

- **[2025-07-07|primary]** Letta/MemGPT defines a two-tier memory hierarchy: 'core memory' consists of in-context memory blocks always present in the context window, while 'archival memory' is explicitly-formulated knowledge stored in external databases and retrieved on demand.
- **[2025-07-07|primary]** The tiered design is explicitly modeled on operating-system memory management: the fixed context window is treated as a constrained resource (RAM-like) and external storage as disk, producing an illusion of unlimited memory within fixed context limits.
- **[2026-03-15|blog]** Letta (the framework descended from MemGPT) implements a three-tier memory hierarchy explicitly analogized to computer memory: core memory as always-in-context RAM, recall memory as a disk cache of conversation history, and archival memory as queryable cold storage.
- **[2026-03-15|blog]** The always-loaded core-memory tier is a small block that the agent reads and writes directly, distinguishing it from the on-demand tiers accessed only via tool calls.
- **[2026-03-15|blog]** Letta's archival/external memory is not passively loaded but retrieved on demand through agent-initiated tool calls during the reasoning loop, i.e. the agent self-curates what to store and retrieve.
- **[2026-03-15|blog]** MemGPT's foundational idea is treating the LLM context window as virtual memory (paging information in and out), which is the conceptual basis for the tiered always-loaded-vs-on-demand model.
- **[2026-03-15|blog]** Letta retrieves long-term memory via agentic tool calls against distinct memory tiers rather than via a passive semantic-search/vector layer (contrasted with Mem0's semantic-search approach).
- **[2026-04-02|blog]** Letta/MemGPT uses an OS-inspired two-tier memory model where core memory is always in-context (like RAM, no retrieval call needed) and archival memory is a separate external vector store the agent queries on demand via an explicit archival_memory_search tool call.
- **[2026-04-02|blog]** In the Letta/MemGPT design the agent itself decides what information moves between the always-loaded and on-demand tiers, i.e. it is an active memory manager rather than a passive recipient of retrieved context.
- **[?|primary]** MemGPT/Letta implements a two-tier memory model: 'core memory' that persists and edits facts (names, dates, preferences) and keeps them available inside the context window, versus 'archival memory' where information is moved to a persistent, searchable external database as conversations grow.
- **[?|primary]** The design frames an LLM agent as an operating system that autonomously manages its own context window, paging information between in-context memory and external storage the way an OS manages memory.
- **[?|primary]** The MemGPT approach and the Letta framework originate from the research paper 'Towards LLMs as Operating Systems' by Charles Packer and Sarah Wooders (Letta co-founders), establishing this as the primary source for the tiered-memory model.
- **[2025-10-17|secondary]** MemGPT splits memory into two tiers: an always-in-context 'main context' (the fixed context window, containing system instructions, writable core-memory blocks, and conversation FIFO queue) and an 'external context' held outside the window that must be explicitly paged in — directly matching the always-loaded core vs on-demand archival two-tier model.
- **[2025-10-17|secondary]** Movement between the two memory tiers is driven by the agent itself via function/tool calls (e.g. core_memory_append/replace, archival_memory_insert/search, conversation_search), i.e. the agent self-edits its own context rather than relying on external retrieval — supporting a curated, agent-managed memory design over automatic RAG injection.
- **[2025-10-17|secondary]** MemGPT's tiered design is explicitly an operating-system virtual-memory analogy: main context maps to RAM/main memory and external context maps to disk, with information paged in and out — grounding the 'core vs archival' memory model in the OS metaphor.
- **[2025-10-17|secondary]** The rationale for managing a limited context via tiers rather than simply enlarging the window is that LLM compute/memory costs scale quadratically with context length and longer windows show diminishing returns because models cannot use the extra context effectively — an argument for a two-tier curated memory over dumping everything into context.
- **[2026-02-22 (updated 2026-06-11)|secondary]** Letta/MemGPT's 'Core Memory' is always held in the LLM context window and stores the agent's persona plus key facts about the current user — the always-loaded tier of the two-tier model.
- **[2026-02-22 (updated 2026-06-11)|secondary]** Letta's on-demand 'Archival Memory' tier is implemented as a vector database for long-term storage that agents write to and retrieve from via search — i.e., the archival tier is vector/RAG-based, not plain markdown.
- **[2026-02-22 (updated 2026-06-11)|secondary]** The tiered design is explicitly modeled on operating-system memory management, using an OS-inspired hierarchy to give LLMs effectively unlimited context beyond the fixed window.
- **[2026-02-22 (updated 2026-06-11)|secondary]** Movement of information between the memory tiers (paging in/out) is driven autonomously by the agent via tool calls, rather than by a fixed retrieval pipeline.
- **[2026-02-22 (updated 2026-06-11)|secondary]** Beyond core and archival, Letta keeps a 'Recall Memory' tier holding full conversation history in a database that agents can search, decoupling long-term recall from the context window.
- **[2026-02-20|blog]** Letta's plain-filesystem memory approach scored 74% on the LoCoMo benchmark, outperforming vector/embedding-based Mem0's 68.5% — evidence that simple filesystems beat complex retrieval pipelines.
- **[2026-02-20|blog]** The article frames the two-tier split via Anthropic's analogy that in-context is like RAM (fast, limited, volatile) while persistent memory is like disk (slower, larger, persistent), mapping to an always-loaded vs on-demand model.
- **[2026-02-20|blog]** A hierarchical/two-tier file layout is recommended: root-level memory files apply everywhere while subdirectory files load only when the agent works in that directory (Claude Code's directory-based loading).
- **[2026-05-01|blog]** The Wiki Builder plugin operationalizes the two-tier compile pattern (Karpathy's raw-sources-as-source-code / wiki-as-compiled-artifact idea): raw material is dropped into a raw/ folder and the coding agent compiles structured markdown pages into a wiki/ folder. This is a working practitioner implementation of the 'compile sources into a wiki' architecture, though the post does not use the word 'compiler' or cite Karpathy by name.
- **[2026-04-23|blog]** The one genuinely useful, transferable idea is not the spatial metaphor but a very low always-loaded 'wake-up' cost (~170 tokens) via a small layered memory stack plus a deterministic, zero-LLM write path — which maps onto a two-tier design's small always-loaded core and argues that curation/inference at write time is optional, not required.
- **[2026-04-02|primary]** The wiki-vs-RAG argument in Karpathy's own linked writeup: RAG re-derives knowledge from raw sources on every query with no accumulation, whereas the wiki compiles knowledge once and keeps it current so it compounds. This is the core justification for choosing a compiled two-tier wiki over vector/RAG retrieval.

## Plain markdown vs vector RAG / scale (11)

- **[2025-07-07|primary]** Retrieval / RAG is characterized as merely a tool that agent memory can use, not as memory itself — i.e., vector/graph databases are storage mechanisms rather than a memory system.
- **[2025-07-07|primary]** Memory blocks are structured units with a label, a description of what they store, a value (the actual in-context tokens), and a character limit, and agents can self-edit them by rewriting specific blocks in response to new information.
- **[2026-04-02|blog]** A pure vector store can retrieve semantically similar facts but cannot represent how facts change over time (validity/supersession), which a temporal knowledge graph can — a stated limitation of vector-only retrieval.
- **[2026-04-02|blog]** On the LongMemEval benchmark, a temporal-graph memory (Zep) scored 63.8% versus a vector-based memory (Mem0) at 49.0%, a ~15-point gap the article attributes to temporal modeling.
- **[?|primary]** The agent edits its own memory through tool-calling and multi-step reasoning (self-editing memory), rather than relying on an external RAG pipeline to decide what to store.
- **[2026-04-03|secondary]** The knowledge base described is at the scale of roughly 100 concept articles totaling about 400K words, which is the concrete scale at which the author argues context-window-plus-index retrieval suffices without vectors.
- **[2026-04-13|blog]** The pattern is bounded by a ~50k-100k token scale ceiling (~150-200 pages); below that line plain file-reading is simpler, more reliable, and cheaper than a RAG pipeline, and only above it does semantic search become necessary.
- **[2026-02-20|blog]** Context degradation ('context rot') is measurable: Claude Sonnet 4 falls from 99% to 50% accuracy on basic tasks as input length grows, so larger context windows only delay rather than solve the memory problem — the core argument that stuffing everything in-context (or RAG-retrieving lots) fails.
- **[2026-02-20|blog]** Effective agent memory files should be kept small and curated — practitioners cap them at roughly 30 items with regular pruning, and a focused 30-item file beats a sprawling 300-item one; this supports deliberate curation over unbounded vector stores.
- **[2026-04-08|blog]** The knowledge layer is deliberately plain structured markdown (summaries, entity pages, cross-references, and a master index) produced by the LLM, rather than a vector index, supporting the plain-markdown design choice over vector RAG.
- **[2026-04-23|blog]** The performance gap between extraction-based and verbatim (store-raw) memory approaches is narrowing sharply — Mem0's April 2026 algorithm jumped LongMemEval from ~49% to 93.4% — weakening any claim that a heavyweight extraction/spatial pipeline is necessary for competitive recall.
